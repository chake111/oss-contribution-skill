## 二、实现前的准备

**在写任何代码之前，请先执行以下操作，禁止边读边写：**
1. 阅读所有需要修改的文件及直接调用方，完整理解当前实现。
2. 检查项目的代码风格与工程规范：
   - 有无 `.eslintrc` / `pyproject.toml` / `ruff.toml` / `.pre-commit-config.yaml` 等配置文件？
   - 现有代码使用的命名风格（`snake_case` / `camelCase` / `PascalCase`）？
   - 注释和 docstring 的书写习惯？
   - 类型标注（Type Hints / TypeScript 类型）的完整程度？
3. 确认当前主分支可以正常运行（跑通 README 中的 quickstart 或现有相关单元测试）。

以上三点任一项不成立时，先修环境或缩小范围。三项都成立就直接进入实现，把检查结论记进任务卡，不停下来汇报。

## 三、实现原则

1. **逐步实现，每步可验证**
   严格按照方案中的实现步骤顺序执行。每完成一步，项目必须仍处于可运行状态，不允许出现中间状态的残缺代码。
2. **最小侵入性**
   - 优先扩展，而不是修改现有函数。
   - 若必须修改现有函数，只改必须改的部分，不顺手做无关重构。
   - 新增的公共接口保持向后兼容。
3. **风格一致性**
   新代码的命名、注释、类型标注风格必须与现有代码保持一致。不引入项目中没有使用的新第三方依赖；确有必要时先确认许可证兼容与安装体积，仍有顾虑就改用标准库或手写实现。

## 四、分步实现流程

### Step 1：接口定义（先定义，后实现）
首先只定义新增的核心接口、类签名、函数签名，不写具体实现（函数体用 `pass` 或 `raise NotImplementedError` 占位）。
完成后先输出以下三项，再直接进入 Step 2：
- 新增了哪些文件 / 接口
- 这些接口如何与现有代码衔接
- 有无发现方案设计时遗漏的依赖或冲突

**接口签名定稿即进入 Step 2，不等确认。** 如果签名在 Step 2 中需要调整，改完在任务卡里记一行原因。

### Step 2：核心逻辑实现
按照实现步骤依次完成每个文件的具体逻辑。每个文件完成后输出：
- 文件路径
- 实现了什么核心逻辑
- 与方案设计有无偏差（若有，说明具体原因）

### Step 3：集成到现有代码
将新模块接入现有的调用链。重点检查并汇报：
- 原有的调用方式是否仍然有效（确保不破坏现有用法）
- 新功能的触发路径是否完整闭环
- 有无遗漏的错误处理分支

### Step 4：验证与测试
按照方案中的验证策略逐项执行：
- **手动验证**：给出一个最小可运行的 demo 脚本或复现命令，直接在终端可以跑通，证明核心功能有效。
- **单元测试**：测试文件放在项目现有的测试目录下，命名风格与现有测试一致，必须覆盖以下场景：
  - 正常路径（Happy Path）
  - 边界情况（如空输入、超长输入、外部调用/工具调用失败）
  - 与现有功能的兼容性（证明原有用法不受影响）

## 六、实现过程中的自主决策规则

**遇到以下情况时自行选一条并继续，不要停下来等回复；决定和依据写进任务卡：**
- 发现方案设计有遗漏，需要改动超出预定范围的文件 → 先把当前 PR 收在原范围内，超出的部分记成后续项；收不回来时更新范围与成功标准，再继续。
- 与现有代码存在冲突，无法在不破坏兼容性的前提下实现 → 选保留旧行为的路径（新增可选参数或新分支），把原方案降级为后续重构。
- 有两种实现方式，各有利弊 → 按“可回滚、调用方无感、测试能覆盖”的顺序取第一条满足的。
- 需要引入新的第三方依赖 → 默认不引入，改用标准库或手写实现；确实绕不开时记录许可证与体积影响。

**遇到以下情况时，可自行处理，但需在实现后明确说明：**
- 方案中的伪代码需要微调以适配实际代码结构。
- 需要补充方案中未提及的常规错误处理逻辑。
- 测试用例的具体断言写法与方案描述略有不同。
