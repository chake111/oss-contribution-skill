## 二、问题边界

先明确以下四项，再比较方案：

- **核心问题**：用一句话说明谁在什么条件下执行什么操作、当前会发生什么，以及期望发生什么。
- **本次 PR 的范围边界**：列出 2～3 项留给后续工作的相邻问题（明确不做什么）。
- **成功标准**：给出可以通过测试或演示观察到的结果。涉及性能或资源消耗时，写明基线、测量方式和目标。
- **约束条件**：
  - 保持现有公共 API 的调用方式和默认行为，明确本次修复预期改变的行为。
  - 根据项目清单和 CI 配置确认适用的语言及运行环境版本（如 Python / Node.js / Go 版本）。
  - 优先复用现有接口、依赖和测试设施。
  - 单个 PR 的改动尽量控制在 300 行以内（按新增行与删除行之和估算，计入测试）。预计超出时，给出拆分点和每个 PR 的验收条件。

## 三、备选方案与推荐结论

给出 2～3 个可行方案。各方案应解决同一个核心问题，并在实现位置、数据流或兼容策略上有实质差异。如果只有一种方案满足约束，说明决定性的约束条件即可。

### 方案 N：{方案名称}
- **核心思路**：用 2～3 句话说明改动放在哪里、如何解决问题。
- **关键设计决策**：
  - 修改或新增哪些类、接口或函数？哪些现有抽象可以直接复用？
  - 数据如何流动？按“输入 → 处理 → 输出”描述一次典型调用，并说明失败时的行为。
  - 在哪个文件、哪个函数与现有模块集成？原有调用方是否需要调整？
- **关键接口或伪代码**：使用项目实际采用的语言，展示关键签名或调用片段。标明哪些符号已经存在、哪些是本方案拟新增的。

- **代价与风险**：说明实现成本、兼容问题和测试难点。
- **适用场景**：说明哪些条件成立时值得选择这个方案。

### 3. 验证策略
- **手动验证**：给出可复现的端到端演示，写明准备条件、操作、改动前的现象和改动后的预期结果。命令以仓库现有脚本为准。
- **单元测试**：列出 2～3 个核心用例。每个用例写明输入、触发条件和关键断言，并指出哪个用例能在修复前复现原问题。
- **边界情况**：沿实际调用链选择相关的异常场景，说明如何触发、系统应如何处理，以及最终应保留什么状态。
- **回归验证**：指出哪些现有调用路径可能受影响，以及哪些已有测试可以验证兼容性。

## 五、维护者沟通草稿

先检查目标 Issue 或 Discussion 的用语和维护者近期回复，据此选择中文或英文。如果仓库明确规定了交流语言，遵循仓库规定。

起草一段可直接发布的评论，语气简洁、专业（中文不超过 150 字，英文不超过 150 词）。评论包含三项内容：
1. 用具体触发条件和可观察结果描述问题。
2. 用一句话概述拟采用的解决方向和改动范围。
3. 询问维护者是否愿意接受这类 PR，以及是否已有相关计划或正在进行的工作。

如果维护者已经回答过其中某个问题，沿用已有结论，只询问尚待确认的事项。
