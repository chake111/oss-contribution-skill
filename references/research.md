# 角色与任务：开源项目贡献机会调研

## 一、项目信息与目标

- **目标仓库**：{REPO_URL}
- **分析基准日期**：{CURRENT_DATE}
- **时间预算**：{TIME_BUDGET，默认：两周内完成实现、测试并提交 PR，合并时间由维护者决定}
- **我的技术背景/偏好**：{TECH_STACK，如：熟悉 Python 异步编程、用过 LangChain/MCP 等}

**我的目标**：找到 1～3 个适合我贡献的 PR 方向。每个方向都应能在时间预算内完成实现、测试并提交 PR，而且能在面试中讲清楚问题如何出现、我为什么选择这个方案，以及如何验证改动有效。

## 二、准备工作

1. 阅读默认分支的 `README.md`、`CONTRIBUTING.md`，以及 `CHANGELOG.md` 或 `HISTORY.md`。文件不存在时跳过。
2. 根据仓库实际结构定位主入口。若为多包仓库，请从 CLI 命令或服务启动入口追踪到核心执行循环，标出相关包、文件和关键函数。
3. 记录分析日期、分支和 commit SHA。源码结论附对应版本的 GitHub 链接，Issue 和 PR 附原始链接。
4. 严格区分“已验证的行为”和“根据源码作出的推断”。如果无法读取仓库、Issue 评论或关联 PR，请指出具体缺少哪项信息，并将受影响的结论标为“待核实”。

## 三、分析维度一：筛选适合贡献的 Issue

访问目标仓库的 Issues 页面（`{REPO_URL}/issues`）。入选的 Issue 须同时满足以下条件：

- 标签至少包含 `good first issue`、`help wanted`、`bug`、`enhancement` 中的一个。
- 状态为 `open`，近 60 天内有过活动，且当前未标记为 `stale`。写出最近活动日期和内容，并区分人工更新与机器人提醒。
- 无 `assignee`。检查评论中是否有人表示 “I'll take this”、“I'm working on this” 或类似认领意向，并核查是否已有进行中的关联 PR。曾有人认领但后来明确退出的，以最新进展为准。
- 描述清楚，能据此确定预期行为、复现步骤或验收条件。
- 根据源码估计，改动能控制在 1～3 个文件内（计入必要的测试文件），且无需整体架构重构。

按下表输出。Issue 编号链接到原文；推荐理由写明最近活动、认领核查结果，以及判断改动范围的依据。若没有符合全部条件的 Issue，说明主要卡在哪些条件上，再继续源码分析。

## 四、分析维度二：核心架构维度深度排查

逐项沿实际调用链检查。已有机制请定位到具体文件和函数；若由类、配置项或事件处理器负责，给出相应符号。判断某项机制缺失时，列出检查过的入口和路径。只有能说明触发条件及实际影响的问题，才列为缺陷。
*（注：以下默认按 AI Agent 架构展开；若目标仓库为其他类型项目，请自动映射为该项目的核心架构链路进行同等深度的排查）*

### 1. 任务规划与主控循环（Task Planning / Execution Loop）
- 当前采用什么规划与执行方式？从执行循环判断其行为接近 ReAct、Plan-and-Execute、其他方式，还是没有显式规划步骤。
- 复杂任务能否拆成子任务？计划在哪里生成，后续由哪个函数读取或执行？
- 某个子任务失败后，系统会重试、调整计划、请求用户介入，还是终止执行？指出对应分支。
- 计划及完成进度是否持久化？会话中断后能从哪里恢复？
- 如果当前依赖模型逐步选择下一项操作，有没有具体任务会因此失败或重复执行？如有，评估引入局部规划机制的成本。

### 2. 多角色/多模块协作（Multi-Agent / Module Coordination）
- 当前有哪些 Agent 或核心工作模块？分别由谁创建、调度和结束？区分核心智能体、普通工具和后台任务。
- 若为单 Agent 架构，指出是否有适合拆成协调者与执行者（Orchestrator + Worker）的具体任务，以及拆分要解决的问题。
- 若已支持多 Agent，追踪一次任务委派：任务如何传递，角色如何分工，执行结果和错误如何汇总？
- 模块之间共享哪些状态？哪些信息需要显式传递？并发执行时如何处理状态冲突？

### 3. 上下文与状态管理（Context & State Management）
- 接近模型 token 上限或内存阈值时，系统如何判断和处理？检查截断、滚动窗口、摘要压缩等策略的触发条件。
- 压缩或截断前后，工具调用与返回值能否保持配对？关键结果、用户约束或未完成任务是否可能丢失？
- 跨轮次的对话历史如何写入、加载和复用？是否存在重复存储或重复发送？
- 系统指令、工具结果和普通对话是否采用不同的保留策略？

### 4. 人工介入与容错恢复（Human-in-the-loop & Checkpointing）
- 执行文件写入、外部 API 调用、消息发送等高风险操作时，哪些条件会触发人工确认？若项目使用置信度信号，也检查它是否参与决策。
- 用户批准、拒绝或修改操作后，执行循环怎样继续？用户反馈是否进入下一轮决策？
- 是否有 checkpoint？分别说明它能恢复哪些内容，例如会话历史、工作区文件或任务执行进度。
- 进程中断或重启后，哪些步骤需要重新执行？对有外部副作用的操作，是否可能重复执行？

### 5. 评估与可观测性（Evaluation & Tracing）
- 是否有 eval 模块、测试集或评估脚本？给出入口、代表性用例和实际检查的指标。
- 评估覆盖最终结果，还是也记录执行轨迹（trajectory），例如工具选择、调用顺序、参数和失败恢复？
- 工具选择正确率、参数有效性等指标是否被量化？项目使用自建流程，还是集成了 LangSmith、Arize 等外部工具？
- 若缺少系统评估，选一个真实任务，估算为它建立最小评估流程的成本，包括用例、判定方式和运行入口。

### 6. 工具检索与路由扩展（Tool Retrieval & Routing）
- 沿一次请求追踪工具注册、筛选和传递过程。模型收到全部工具定义，还是按任务获得一个子集？工具定义通过哪个请求字段传递？
- 当可用工具超过 20 个时，是否有按名称、规则、语义或向量检索来选择工具的机制？说明该场景是否能在当前项目中出现。
- 是否存在职责或描述相近的工具？若判断容易误选，请给出具体工具对，并区分实际误选记录与推测。
- 是否支持 MCP（Model Context Protocol）或通用插件协议？若支持，定位工具的发现、注册和调用入口；若缺失，评估接入现有工具层需要改哪些位置。

### 7. 流式输出与中间状态可见性（Streaming & Visibility）
- 响应是否支持增量流式输出？追踪从底层返回片段到终端或前端渲染的路径。
- 哪些中间状态对用户可见？检查当前子任务、正在调用的工具、调用参数、执行结果及错误状态。
- 是否有事件或状态订阅接口供界面展示执行进度？列出代表性事件、生产者和消费者。
- 如果某项进度不可见，定位信息在哪一步丢失，并评估复用现有事件通道的改动成本。

### 每个维度统一输出格式
1. **现状描述**：给出 `文件路径 → 函数、类或事件`，说明相关调用关系。
2. **缺陷或缺失**：写出触发条件、实际行为和影响。证据充分时给出最小复现步骤；没有发现具体问题时写“未发现明确缺陷”。
3. **影响程度**：`high` / `medium` / `low`，并说明评级依据。没有明确缺陷时填“不适用”。
4. **改进方向**：用 1～3 句话说明可行的改动及验收方法。
5. **改动范围**：估算涉及的文件数和代码行量级，分别说明实现和测试的工作量。
6. **面试叙事角度**：用一句话指出这个贡献能体现哪项技术判断或工程能力。

## 五、最终输出：按优先级推荐最多 3 个 PR 方向

综合 Issue 筛选和源码分析，优先考虑问题已验证、时间预算内可提交、验收标准明确，而且适合结合我的经历讲述的方向。同一问题同时来自 Issue 和源码分析时，合并为一项。对自行发现的问题，先核查是否已有相同 Issue、关联 PR 或维护者意见。

每个方向按以下格式输出：

### 第 N 名：{PR 方向名称}
- **一句话描述**：在什么场景下，准备解决什么问题？
- **来源**：Issue #xxx / 代码分析第 X 维度，附链接。
- **入口文件**：从哪个文件、函数开始？预计还要改哪些实现或测试文件？
- **为什么适合我**：我能复用哪些已有经验？需要补学什么？
- **预计工作量**：小 / 中 / 大，给出预计人日，计入环境搭建、复现、实现和测试。
- **验收标准**：用什么命令、测试用例或可观察行为来判断改动成功？
- **面试中能讲什么**：围绕一个具体技术决策，说明可选方案、选择依据，以及可以拿什么测试结果证明改动有效。
- **风险点**：列出可能影响提交的依赖、维护者意见或范围变化，并说明最先需要核实哪一项。

有几个符合条件的方向就推荐几个。如果没有合适方向，说明关键阻碍。涉及面试叙事时，将尚待实施的工作写成计划，验证结果留到实际完成后填写。
